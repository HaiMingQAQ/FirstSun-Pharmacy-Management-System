## 续开发记录：P0 显式分配与货位数量

用户要求继续后，再次 fetch 成功；main/A/D 提交号均未变化，协作和环境阻塞仍在。继续仅修改 C 规则和测试，没有操作共享库或公共配置。

- `validateExplicit` 校验单行指定批次/货位，重复项先合并，行数量必须与分配合计相等。库存不足、过期或停售时拒绝，不自动换到其他批次。返回按 batchId/locationId 排序的不可变结果。
- `allocateLines` 为同一药品的多条明细共用剩余可用量；要求稳定且不重复的来源行 ID，按 ID 升序分配，支持自动/显式混用。所有行成功才返回；任何行失败不修改输入快照。一次计算只读取一次时钟，避免跨午夜的行内日期分歧。
- 候选检查增加“同一 locationId 不得归属两个 warehouseId”，即使两仓均在允许范围也拒绝矛盾快照。
- `LocationQuantity.receive` 接收整货位实际占用汇总，计算容量时包含其他药品、批次和冻结量；NULL 容量不限制，0 容量禁止新增。支持最大容量 4294967295，并拦截行数量和聚合加法溢出。普通销售不减少冻结量。
- 这里只提供库内算法值对象 `RequestLine`、`Selection`、`PlannedLine`，没有宣布与 D 的 DTO 已冻结。`allocateLines` 一次只处理一种药品，服务层必须先对整单按药品分组并规划全部组，再在同一事务里落库；单独调用 `allocate`/`validateExplicit` 多次不能代替整单校验。

同一 verify-rules.ps1 命令实际先通过 32 组，补齐整单分配后最终结果为：

```text

```

新增 18 组检查涵盖显式重复项、合计不符/溢出、不可替换失效分配、跨仓货位冲突、容量空值/零值/无符号边界、整货位占用、批次与货位联合收售退守恒、多行合计超卖、自动/显式共享余额、来源行重复、输入列表防御性复制和跨午夜日期一致性。Java 8 兼容编译及源码 lint 通过；真实 MySQL、服务权限、HTTP、页面和截图仍未验证。

新增 `ReceiptBatchMetadata` 与 `SaleReturnPlanner`，仅在 C 的 rule 目录及原规则检查文件改动：

- 收货的生产日期不能晚于有效日期；复用批次必须同时保持两项日期一致，NULL 不允许静默替换为已知日期，反向亦然。实际批次应由数据库唯一键查找，不用 Java 字符串比较模拟 MySQL 批号排序规则。供应商和成本策略仍待确认。
- 退货请求值只含稳定来源行 ID、原出库 flowId、qty；批次、货位、药品和 unitCost 从原流水快照取，不允许请求覆盖。只接受销售出库类型 20/82；82 只是识别历史销售流，不实现 P2 冻结转出库。
- 同一原流的多条退货明细共同扣减剩余可退量。已经退回数量必须来自加锁后数据库汇总；内存规划不能解决两事务并发回补。原流是否属于已授权销售、是否已删除、是否正常质量退货，仍由待实现的服务校验。
- 成本按已有 DECIMAL(18,4) 验证，不进行隐式舍入。回补后的库存加权成本尚未实现，不将“保留原流成本”误写成完整成本核算。
- 现有 uk_flow_event 限制同一来源行/批次/货位/类型只能一笔流。同一来源行引用两笔相同批次货位的原流，现阶段明确拒绝；由 D 确认真实拆行 ID 或团队另审迁移，不合并丢失原流引用。不同来源行仍可合法部分回补同一原流。
