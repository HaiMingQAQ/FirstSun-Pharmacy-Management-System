## D：已有调用点的具体调整建议

相关路径均位于 `backend/yudao-module-pharmacy/src/main/java/cn/iocoder/yudao/module/pharmacy/`，只读检查，未修改。

1. `service/sale/impl/SaleOrderServiceImpl.java#createSaleOrder` 已在事务中插入销售单和明细，但构造 DeductItem 时遍历原请求，遗漏已生成的明细 ID。建议改为从已插入 `lines` 构造请求，携带 orderNo、line.id、drugId、qty、显式 batchId/locationId。一次全单调用，不逐行开启库存事务。
2. 同一方法当前不消费扣库返回结果。新版调用应保存实际 flowId/批次/货位分配与四位成本快照，完成来源明细与库存流可追溯关联。D 决定自身表如何保存，C 不直接改销售表。
3. `service/sale/impl/SaleReturnServiceImpl.java#createReturn` 当前先调用 returnBack，后插入退货单和明细。建议 D 在同一本地事务先创建稳定退货单号及明细 ID，再按原出库 flowId 调用 C，最后完成退货状态；任何失败全部回滚。不能用原销售行 ID 代替退货行 ID，也不能用时间戳或药品组合猜造业务键。
4. `api/inventory/InventoryFacade.java`、其 DTO 和 `config/FacadeFallbackConfiguration.java` 由 D 确认迁移方式。旧签名缺来源不能实现成成功兼容层。确认后由 D 的适配器调用 C InventoryApi，验证只有一个有效 Bean，保留失败占位直到真接入。
5. 最小接入先使用显式分配，D 已要求 batchId/locationId。AUTO_FEFO 跨批拆行需另外确认源行 ID 与库存分配一对多的落库方式。预览不占库，正式提交仍可不足并要求刷新。

拟确认的方法及字段（尚未实现对外接口）：

| 方法 | 输入 | 输出 |
| --- | --- | --- |
| receive | storeId、bizType=1、bizNo=收货单号；全部行带收货行 ID、药品、仓库、货位、批号、日期、供应商、qty、unitCost | operationId、replayed、实际分配 |
| deduct | storeId、bizType=2、bizNo=销售单号；全部行带销售行 ID、drugId、qty、明确分配或 AUTO_FEFO | operationId、replayed、实际分配 |
| returnBack | storeId、bizType=3、bizNo=退货单号；行带退货行 ID、originalFlowId、qty | operationId、replayed、实际分配 |

实际分配含 bizLineId、flowId、batchId、batchNo、expiryDate、locationId、qty、unitCost、balanceQty。输入不带可信租户/操作者；服务上下文提供。失败抛异常，加入来源业务 REQUIRED 事务；不以 success=true 返回部分成功。

### 已有 C 内部规则如何接入（尚非对外 API）

`FefoAllocator.validateExplicit` 已能严格校验单条来源行的显式批次/货位，无法满足时失败，不换批。`allocateLines` 已能对同药品全部来源行共同分配，防止各行单独充足但整单超卖。调用顺序仍必须是：可信身份与来源验证、操作级幂等读取/重放、仓库锁与作业门禁、重新读取候选及校验主数据/三账、整单所有药品规划、批次/货位/流水/操作结果落库。纯算法没有完成上述服务接入。

内部 `RequestLine.sourceLineId` 对应未来稳定 bizLineId；`PlannedLine` 仅有来源行 ID 及 batchId/locationId/qty，尚无数据库生成 flowId、operationId 或成本。不能把规划结果当作已出库成功响应。按来源行 ID 升序分配是当前算法的稳定顺序，D 接入评审应核对与拆行方案一致。

`LocationQuantity.receive` 的占用参数必须来自已锁仓库内整货位汇总，含所有药品/批次与冻结数量；不能只传当前批次数量。计算值用于收货及已验证原出库的退货回补，不能独立绕过原流关联、容量、来源状态或事务。

2026-09-11 补充：`SaleReturnPlanner` 已按原销售流水规划回补，原 batchId/locationId/unitCost 均取可信快照；同一原流的整单多行共用可退量。它不读数据库，不提供已执行成功响应。

新增需要 D/A 确认的精确冲突：如果一个退货 bizLineId 引用两个 originalFlowId，且两个原流具有相同 batchId/locationId，现有 `uk_flow_event` 会冲突，单个 `original_flow_id` 又无法同时保留两个引用。建议 D 将其拆为有真实持久化 ID 的不同退货明细；若 D 无法拆行，需要另审关联模型/唯一键迁移。C 当前规划器拒绝该输入，不自行加后缀、伪造行 ID 或覆盖原引用。

## B：收货与事务入口

需 B 确认以每张已通过验收的收货单作为唯一事件，分批收货使用不同单号。B 提供稳定 receipt line ID，在同一主库事务中调用 C，再回填 create_batch_id 和来源状态。确认同批号不同供应商处理、成本四位及金额舍入；C 不更新采购表。

## A/B/C：迁移批准项与顺序

没有执行以下 DDL，也没有修改 46 表初始化脚本。文件名是建议，不是已存在的迁移。

1. 确认独立数据库及对应 MySQL 8.0.28+，先按 `preflight-readonly.sql` 检查实际 schema 和历史冲突。脚本不会修改表；不要用空结果推断完整业务正确。
2. 拟新增 `sql/migrations/20260910_c_inventory_operation.sql`：ph_inv_operation，主键 BIGINT；tenant_id/store_id，operation_type，biz_type，biz_no VARCHAR(32)，request_hash CHAR(64)，result_json JSON，operator 及审计时间；唯一键 `(tenant_id, store_id, operation_type, biz_type, biz_no)`。这是成功事件不可变凭据，无重做用软删除。批准后表数为 47。
3. 拟新增 `20260910_c_inventory_flow_trace.sql`：ph_inv_flow 增加 nullable operation_id/original_flow_id BIGINT；索引 `(tenant_id, operation_id)`、`(tenant_id, original_flow_id)`。历史 NULL 不伪造原出库引用；需要补录/切换策略，无法核验的历史退货拒绝自动回补。
4. 拟新增 `20260910_c_inventory_default_warehouse.sql`：生成列仅在 deleted=0、status=1、is_default=1 时返回 store_id，否则 NULL；tenant_id+生成列唯一。若预检有重复，停止迁移，由负责人处理；不自动删除/改写历史默认仓。
5. P0 完成后单独批准 P1 迁移：盘点取消/驳回人员意见时间及行版本快照、报损复核时间/意见和四位成本快照；追加审计走 A 确认接口；待上架货位标识、移位 flow_type/biz_type 数值另确认。不得擅改既有状态或枚举。

MySQL DDL 不能依靠业务事务回滚。批准后的脚本必须有版本检查、重复执行说明，在独立空库和基线升级副本分别验证；失败后检查实际 schema，不自动重跑整套建库或删数据。本轮没有执行迁移，故没有可声称的迁移验证结果。
