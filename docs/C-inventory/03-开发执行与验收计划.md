## 3. 最小环境核验

先只读检查已安装版本、仓库与服务状态，再决定如何运行。现有 Docker 使用固定容器名 `firstsun-pharmacy-*`，复制一个目录不会自动隔离容器；`docker compose -p` 也不能消除固定 container_name 冲突。确认这些服务属于本人后才启动/重建，不操作共享联调库。

- 确认 Java/Maven/Node/pnpm/Docker 可用及版本与集成基线兼容。
- 确认 MySQL 是本人的独立数据库及正确 schema；不要打印含密码的完整配置或命令行。
- 确认 Redis、MySQL、后端和前端端口占用，不自动停止未知服务。
- `.env` 和个人配置只保存在本机；新库初始化与现有库增量迁移分开。
- 先建立基线启动/构建结果，再报告新增代码造成的回归；不修复任务外全仓问题来扩大范围。

## 4. 测试矩阵

以下都是待执行测试，启动阶段未运行。针对交易行为设计测试，避免仅断言 getter、字段名或映射存在。

| 测试 | 输入/操作 | 预期 |
| --- | --- | --- |
| T01 资料唯一性 | 同门店重复仓库码、同仓库重复货位码；并发设两个默认仓 | 明确冲突，最终最多一个启用默认仓 |
| T02 归属验证 | 给门店A请求传入门店B仓库/货位/批次 | 拒绝，数据库无写入、无跨店数据泄露 |
| T03 批次复用 | 相同唯一键相同日期再次收货；同键换有效日期 | 前者合并数量/成本，后者冲突，历史元数据不被改写 |
| T04 收货幂等 | 同收货单同明细提交两次、并发两次 | 一组操作记录与流水，数量只增加一次 |
| T05 请求冲突 | 同业务键改数量、货位或成本 | 返回幂等参数冲突，不能吞为原成功 |
| T06 FEFO | 两批有效期不同，跨货位且先插入晚效期批次 | 按效期分配，顺序稳定且合计准确 |
| T07 选批重放 | 首次扣库后，原批次耗尽，再重发原请求 | 返回原分配，不转向下一批次重复扣库 |
| T08 不足库存 | 在库5扣6；或冻结4时普通销售扣2 | 全部失败，所有批次/货位/流水/操作记录保持原值 |
| T09 并发销售 | 在库5，两个不同业务单同时各扣4 | 至多一个成功，剩余1，任何时点提交态无负库存 |
| T10 事务回滚 | 第二批次/流水插入处注入失败；B/D外层业务更新失败 | C及来源业务全部回滚，不残留第一批更新或成功幂等记录 |
| T11 效期/质量 | 固定时钟测前一天、当天、后一天；quality停售/召回 | 符合确认后的边界，异步expiry_status落后也不能放行 |
| T12 非销售操作 | 对过期库存合法报损，对停售药品查历史 | 可受控执行，不误用销售有效性校验全部拦截 |
| T13 部分退货 | 原出库5，退2再退3，再退1；同一退单重复 | 前两次成功，第3次拒绝；重复保持数量不变 |
| T14 并发退货 | 原剩余可退3，两张退货单同时各退2 | 总回补不超3，sold不为负，原流水关联正确 |
| T15 单位/成本 | 小数或负数量、越界整数；重复收货不同成本 | 无非法数量；4位成本/2位金额符合规则，无二进制浮点误差 |
| T16 上架 | 源2移动3、移动冻结部分、目标超容量、重复移动 | 拒绝非法请求；合法源减目标增、总量守恒、流水成对 |
| T17 盘点 | 实盘NULL、0，盲盘用户查详情，盘点期间新收货 | NULL阻止完成；0正确计算；账面数不泄露；写入门禁有效 |
| T18 盘点状态 | 审批前调整、驳回修改、重复审批、取消 | 非法转换拒绝；审批一次入账；取消不改库存且解门禁 |
| T19 报损身份 | 未审批执行；执行人自填复核人ID；同人复核执行 | 拒绝；真实不同登录身份且状态满足才执行 |
| T20 报损竞争 | 审批后库存已不足；重复执行 | 失败整单不出账；成功重复不重复扣减 |
| T21 每日预警 | 同日并发刷新、30/60/90天边界、已过期 | 每批每日最多一条；分级不重叠；继续销售不绕过有效期 |
| T22 三账 | 正常闭环、缺期初流、故意制造差异的测试库 | 正常相等；缺基线与差异明确报告，不自动修正 |
| T23 权限 | 无权限账号直接调用API、他店ID、成本受限用户 | 后端拒绝越权；前端按钮同步隐藏；无敏感成本返回 |
| T24 UI反馈 | 网络错误、无数据、快速重复点击、窄屏 | loading恢复，显示错误，重复受后端保护，操作不遮挡 |
| T25 冻结扩展 | 锁定/释放/消费重复、支付取消竞争、锁后过期 | 只一个合法终态；冻结与锁守恒；失效库存不可转销售 |
| T26 升级迁移 | 独立新库初始化；已有基线库应用新增迁移 | 两者可用，既有数据不丢；重复执行行为按脚本说明，不依赖自动扫描 |

事务、唯一约束、行锁、CHECK 与并发验收必须在匹配版本的 MySQL/InnoDB 上验证。仅 H2/Mock/内存单测通过，不能证明 MySQL 库存并发正确。

## 5. 拟用验证命令

下面是开发阶段命令模板，不是本轮执行记录。先确认模块、依赖和测试运行配置已存在；本机数据库参数不要写入提交或共享文档。

```powershell
# 仓库根目录，只读检查
git status --short --branch

git diff --check

# backend，公共模块接入且测试环境就绪后
mvn -pl yudao-module-pharmacy -am test

# admin-ui，使用已有锁文件，依赖可用后
pnpm install --frozen-lockfile
pnpm ts:check
pnpm exec eslint src/views/pharmacy/inventory src/api/pharmacy/inventory
pnpm exec prettier --check "src/views/pharmacy/inventory/**/*.{vue,ts}" "src/api/pharmacy/inventory/**/*.ts"

```

`package -DskipTests` 仅证明构建，不证明交易测试通过。需核对 Surefire 等测试报告中的实际运行数量，防止 0 tests 被当作通过；集成测试若另配 profile，记录精确命令和目标库性质。不要运行全仓自动格式化改动其他成员文件。
