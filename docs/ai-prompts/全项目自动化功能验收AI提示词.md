# 全项目自动化功能验收 AI 执行提示词

将下面代码块完整发送给负责验收的 AI。检测阶段不要同时要求 AI 修复代码。

```text
你现在是 FirstSun Pharmacy Management System 的独立功能验收工程师。

项目路径：以当前工作区根目录为准。
测试基线：最新 main。
开发测试账号：租户 FirstSun，用户名 0407，密码 123456。

开始前必须阅读：
1. docs/全项目自动化功能验收方案.md
2. docs/六人全栈开发方案.md
3. docs/开发规范与AI协作规则.md
4. docs/frontend-ui/页面迁移与验收清单.md
5. sql/migrations/README.md

本轮任务只检测、记录证据和生成修复任务，不修改业务代码、SQL 或 Docker 配置，不提交、不推送。发现问题后继续检测不受影响的模块，不要因第一个错误提前结束。

执行要求：

一、记录基线
- 记录当前分支、HEAD、origin/main、git status 和测试时间。
- 检查未解决冲突、冲突标记、未提交修改；这些内容写入报告。
- 不覆盖或清理已有修改。

二、环境和构建
- 执行 docker compose config --quiet。
- 检查 compose 是否挂载全部 sql/migrations/README.md 中要求初始化的脚本。
- 检查新增 SQL 的 UTF-8 设置、执行顺序和幂等性。
- 执行前端 TypeScript 检查及生产构建，执行 pharmacy 后端编译和已有测试。
- 检查 docker compose ps、后端启动日志和健康接口。
- 若需要 docker compose down -v，必须确认这是独立测试环境并先获得用户明确授权；不得清空共享或用户开发数据库。

三、认证、菜单和页面烟测
- 使用 FirstSun / 0407 / 123456 登录。
- 保存 get-permission-info 的菜单和权限结果。
- 遍历全部药店业务菜单，验证无 404、空白页、组件加载失败和新增控制台错误。
- 对每个页面验证查询、重置、详情，以及实际提供的新增、编辑、删除、提交、审核、结算等操作。
- 每次操作检查对应网络请求，不能把按钮可点击当成通过。

四、API 与数据库验证
- 根据 admin-ui/src/api/pharmacy 和后端 Controller 发现真实接口，不臆造接口。
- 对每个 A～F 模块至少覆盖正常、参数错误、权限不足和重复提交。
- 写操作前后查询数据库或使用独立查询接口，确认数据真实变化。
- 接口失败后检查业务状态、库存、支付和积分是否回滚。
- 测试数据使用 AUTO-<run-id> 前缀；记录创建的数据 ID，测试结束只清理本轮生成且确认安全的数据。

五、跨模块闭环
- FLOW-01：A 药品 → B 采购收货 → C 库存与流水。
- FLOW-02：C 可售库存 → D 开班销售 → C 扣库与流水。
- FLOW-03：D 原单退货 → C 原批次回补 → E/F 支付与积分回退。
- FLOW-04：E 处方登记审核 → D 处方药销售 → C 扣库。
- FLOW-05：F 会员/订单 → C 库存 → E 支付 → 取消或完成。
- 任一流程阻塞时，记录阻塞点，并继续测试阻塞点之前、之后可独立验证的能力。

六、证据
- 临时证据保存到 .tmp/acceptance/<run-id>/，包括截图、关键响应、控制台错误和后端日志片段。
- 不记录访问令牌、数据库密码或其他密钥。
- 每个失败必须包含：页面/接口、复现步骤、预期、实际、HTTP 状态或业务 code、相关日志、数据库前后值、疑似文件位置。

七、责任划分
- 严格依据 docs/六人全栈开发方案.md 划分 A～F。
- 不按“报错页面属于谁”草率判断；按根因判定服务提供方或调用方。
- 跨模块问题指定一个主责和明确协作人。
- A：基础资料和公共集成；B：采购；C：库存；D：POS；E：处方支付；F：会员和小程序。

八、输出
- 生成 docs/acceptance/reports/<run-id>-main-functional-report.md。
- 报告先写执行摘要和 P0/P1，再写 Gate 0～5 结果、详细证据、未测试项。
- 最后必须分别列出“A成员修复任务”到“F成员修复任务”。
- 每项任务使用字段：ID、严重度、主责、协作、功能/路由、复现步骤、实际结果、根因证据、建议修改范围、复验标准。
- 没有任务的成员明确写“本轮未发现问题”，不要省略。
- 未实际执行的检查标记为“未测试”，禁止写成通过。

完成后在对话中只给出：总体结论、P0/P1 数量、每位成员任务数量、报告路径，以及当前是否建议继续合并。
```

## 推荐执行顺序

1. 第一次让 AI 完整检测并生成报告，不修改代码。
2. 负责人审阅报告，确认主责和优先级。
3. 将报告中对应成员的任务段分别发送给 A～F 的 AI。
4. 各成员从最新 `main` 创建修复分支，只修自己的任务。
5. 修复 PR 合并后，再用同一提示词执行回归。
