# A 成员 AI 开发提示词

> 使用方法：开始一个新的 AI 编程会话时，先发送“主提示词”，再发送本次任务模板。一次只安排一个可以独立验证的小任务。

## 一、主提示词

```text
你正在协助我开发 FirstSun 药店管理系统。请把以下内容视为本次会话的开发约束，并在整个会话中持续遵守。

【项目背景】
- 项目基于 ruoyi-vue-pro / yudao-vue-pro 二次开发，不从零重写框架。
- 项目根目录：以当前 AI 工具打开的 Git 仓库根目录为准。开始前通过 Git 和目录结构确认，不要写死个人电脑的绝对路径。
- 后端目录（相对项目根目录）：backend
- 管理端目录（相对项目根目录）：admin-ui
- 小程序目录（相对项目根目录）：mall-uniapp
- SQL 目录（相对项目根目录）：sql
- 后端技术栈以仓库现状为准；管理端使用 Vue 3、TypeScript、Element Plus 和 pnpm。
- 本地环境由 docker-compose 管理，包含 MySQL、Redis、后端和管理端。
- 如果 AI 当前打开的目录不是项目仓库，或找不到 .git、backend、admin-ui、mall-uniapp、sql 和 docker-compose.yml，请先提示我打开正确的仓库，不要在其他目录创建同名工程。

【我的身份与职责】
我是 A 成员，负责“基础资料与公共平台”，同时兼任工程集成负责人。

我的业务范围：
1. 建立或维护 backend/yudao-module-pharmacy，并接入 yudao-server。
2. 管理端 pharmacy/base 下的门店、员工、药品分类、药品和药品条码功能。
3. 配置 system 模块中的菜单、角色、按钮权限和必要字典，但不重写 system 核心能力。
4. 实现主数据 CRUD、条码唯一性、药品停用校验、员工与 system 用户的关联。
5. 向 B、C、D、F 提供稳定的药品查询和条码查询接口。
6. 汇总菜单 SQL 和数据库增量迁移，但不代替其他成员开发其业务模块。

我主要维护的业务表：
- ph_store
- ph_employee
- ph_category
- ph_drug
- ph_drug_barcode

【允许修改的主要范围】
- backend/yudao-module-pharmacy/** 中属于基础资料域的代码
- backend/yudao-server 中接入 pharmacy 模块所必需的最小配置
- admin-ui/src/views/pharmacy/base/**
- admin-ui/src/api/pharmacy/base/**（若现有项目的接口目录结构不同，遵循仓库实际结构）
- sql/migrations/** 中由 A 负责的增量 SQL
- 与本任务直接相关的菜单、权限和字典 SQL

【修改限制】
- 开始前先读取仓库结构、现有同类模块、项目说明和团队规范，不猜测类名、包名、版本或目录。
- 优先仿照 yudao 现有 CRUD 模块的 Controller、Service、Mapper、VO、权限、异常码和前端页面写法。
- 不重写登录、用户、角色、菜单、字典、文件上传、会员和支付能力。
- 不直接修改 B～F 负责的采购、库存、销售、处方支付、会员及小程序订单代码和表。
- 不擅自升级依赖、引入新 UI 框架、改变全局主题、修改公共组件或重构无关代码。
- 如果必须修改公共文件或其他成员范围，先说明文件、原因和影响，等待我明确同意；同时继续完成不依赖该变更的工作。
- 不提交 .env、密码、密钥、node_modules、target、日志或真实业务数据。
- 未经我明确要求，不执行 git push、不创建或合并 PR、不操作共享数据库、不清空 Docker 卷。
- 保留工作区中已有的未提交改动，不覆盖或撤销他人代码。

【后端与数据库规则】
- 使用 yudao 已有的统一响应、异常、权限、分页、审计字段和数据权限机制。
- 后端必须校验参数、权限、数据归属和业务状态，不能只依赖前端校验。
- 药品条码必须保证唯一；药品停用后，商品查询接口必须返回明确状态，供销售等模块拦截。
- 删除被业务数据引用的主数据前必须校验；不要简单物理删除导致关联记录失效。
- 数据库变更使用新的增量 SQL，已执行的迁移文件不改写。
- 增量 SQL 文件名格式：YYYYMMDD_a_具体内容.sql。
- 先核对 firstsun_pharmacy_init.sql 的实际字段，再编写实体和 SQL，不凭分工文档虚构字段。

【跨模块接口契约】
商品查询和条码查询至少应明确：药品 ID、分类、名称、规格、条码、销售价格、是否处方药、启用/停用状态。
在接口实现前，先列出请求字段、响应字段、权限标识、错误情况和调用方；未经协调不要随意改变已经公布的契约。

【前端规则】
- 遵守《前端界面统一规范》，复用项目现有组件、布局、主题变量和交互模式。
- 管理页保持统一结构：查询区、操作区、表格、分页、抽屉或弹窗表单。
- 不自行设计一套颜色、按钮、表格或弹窗风格，不在业务页面修改全局 CSS。
- 页面文案使用简洁、统一的中文业务术语。
- 必须实现加载、空数据、校验失败和接口失败状态，不能用 Mock 数据冒充联调完成。

【工作方式】
1. 先说明你读取了哪些关键文件，并概括现有实现。
2. 给出不超过 6 步的实施计划，每一步写明验证方法。
3. 只修改本次任务必需的文件，保持改动最小。
4. 实现后执行与改动相称的编译、检查或测试，并修复由本次改动造成的问题。
5. 如果需求与数据库或现有代码冲突，停止相关修改，清楚列出冲突和可选方案，不静默猜测。

【完成时必须报告】
- 已完成的功能和实际行为
- 修改及新增的文件
- 接口和权限标识
- 数据库迁移文件及执行要求
- 实际运行的验证命令和结果
- 未验证项、依赖项和需要其他成员协调的事项

现在先不要修改代码。请先检查项目结构、相关规范和当前 Git 状态，然后等待我提供“本次任务”。
```

## 三、建议的第一个开发任务

不要一开始同时生成五张表的全部前后端。建议先建立模块骨架，再以“药品分类”完成第一条全栈链路。

```text
【本次任务】
任务名称：建立 pharmacy 后端模块骨架，并完成药品分类的最小全栈闭环
业务目标：yudao-server 能加载 pharmacy 模块；管理员可以在管理端分页查询、新增、修改和启停药品分类。
允许修改的目录或文件：
- backend/yudao-module-pharmacy/**
- backend/yudao-server 中接入该模块必需的最小文件
- admin-ui/src/views/pharmacy/base/category/**
- admin-ui/src/api/pharmacy/base/category/**（按实际结构调整）
- sql/migrations/**
需要读取的参考页面或后端模块：选择仓库内一个结构最接近的 yudao CRUD 模块作为唯一主要范例。
涉及的数据表：ph_category；如现有表字段不足，只提交必要的增量 SQL，不新增业务表。
权限标识建议：pharmacy:category:query、create、update、delete（最终以项目既有格式为准）。
验收步骤：
1. 后端编译通过并成功启动。
2. 菜单可访问，且无权限账号无法访问接口。
3. 分类列表支持分页和条件查询。
4. 新增、修改和启停后可从数据库查到真实结果。
5. 非法参数、重复数据和被引用分类的删除行为有明确处理。

先检查数据库字段和现有模块风格，再确认实际文件清单。完成后报告验证结果，不自动推送代码。
```

## 四、A 成员建议开发顺序

1. `yudao-module-pharmacy` 模块骨架与 `yudao-server` 接入。
2. 药品分类全栈闭环，作为全组参考页面。
3. 门店管理。
4. 员工管理及 `system` 用户关联。
5. 药品档案。
6. 药品条码及唯一性校验。
7. 商品查询、条码查询跨模块接口。
8. 菜单、角色、权限、字典及迁移脚本汇总。
9. A 模块自测和跨模块契约联调。
