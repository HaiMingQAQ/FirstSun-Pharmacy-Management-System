# AI 助手单人技术原型开发提示词

> 使用方式：将以下“完整提示词”整体复制给编码 AI。该提示词用于单人完成最小技术原型，不代表正式生产版本。

## 完整提示词

```text
你现在是本项目“AI 助手技术原型”的唯一全栈开发者。请在现有仓库中完成一个可运行、可验证的最小原型。

【项目路径】
D:\github-2\FirstSun Pharmacy Management System

【必须先阅读的资料】
1. docs/开发规范与AI协作规则.md
2. docs/AI助手可行性分析与实现方案.md
3. E:\github\xmlg-2\2-资料2\小型药店管理系统AI知识问答技术方案.md

如参考资料与当前仓库实际代码冲突，以当前仓库的数据表、Service、权限体系和依赖版本为准，并在交付说明中记录差异。

【任务目标】
由一人完成一个管理端 AI 助手技术原型，验证以下完整闭环：

1. 登录用户可以进入“AI 助手”页面并发送自然语言消息；
2. 后端通过 SSE 流式返回回答；
3. AI 可以调用白名单工具查询药品档案；
4. AI 可以查询当前用户所属门店的药品库存；
5. AI 可以为药品新增、修改、删除生成结构化操作预览；
6. 写操作在用户明确点击确认之前不得写入数据库；
7. 确认后必须调用现有 Pharmacy Service 执行，并返回真实结果；
8. AI 服务失败时不得影响原有药品、库存、POS 等业务功能。

这是技术原型，不建设正式生产级 RAG，不追求一次覆盖全部药店业务。

【开始开发前】
先检查并报告以下内容，然后给出简短实施计划：

1. 当前 Git 工作区是否存在用户未提交修改；
2. `backend/yudao-module-ai` 的实际结构、依赖版本和启用状态；
3. `backend/yudao-module-pharmacy` 中可复用的 DrugService、EmployeeService 和库存查询 Service；
4. 管理端现有 AI 页面、API、SSE 实现及可复用组件；
5. 当前菜单、权限、租户和门店隔离实现；
6. 预计需要修改和新增的文件。

不要覆盖、回退、格式化或清理用户已有的无关修改。发现不相关问题只记录，不顺手修复。

计划格式：

1. [实施步骤] → 验证：[具体检查]
2. [实施步骤] → 验证：[具体检查]
3. [实施步骤] → 验证：[具体检查]

给出计划后直接继续实施；只有出现会显著改变范围、安全模型或数据结构的歧义时才询问用户。

【原型范围】

一、必须完成

1. 管理端 AI 助手页面；
2. POST + SSE 流式对话；
3. 药品模糊搜索；
4. 药品详情查询；
5. 当前门店库存查询；
6. 药品新增预览与确认；
7. 药品修改差异预览与确认；
8. 药品删除目标预览与确认；
9. 基本权限、租户和门店隔离；
10. 最小必要的操作日志或命令状态记录；
11. 单元测试和关键集成测试；
12. 配置、启动和验证说明。

二、明确不做

1. 不建设向量数据库、Embedding、Rerank、文档切分和知识库管理；
2. 不开发药品说明书或 GSP 文档 RAG；
3. 不开发微信小程序 AI 助手；
4. 不允许 AI 调整库存、生成库存流水、执行盘点或报损；
5. 不允许 AI 执行采购审批、收货入账、处方审核、销售结算、支付或退款；
6. 不允许 AI 生成或执行任意 SQL；
7. 不升级与本任务无关的框架和依赖；
8. 不重构现有药店业务模块；
9. 不增加语音、图片识别、多模型切换等附加功能；
10. 不部署生产环境，不操作共享数据库。

【关键事实】

1. `ph_store` 是门店表，不是药品或库存表；
2. 药品档案表是 `ph_drug`；
3. 批次库存表是 `ph_inv_batch`；
4. 货位库存表是 `ph_inv_location_stock`；
5. `tenant_id` 只能提供租户隔离，不能代替 `store_id` 门店隔离；
6. 当前门店应优先通过登录用户和 `EmployeeService.getEmployeeByUserId(userId)` 在服务端解析；
7. 模型或前端提交的 `tenantId`、`userId`、`employeeId`、`storeId` 均不能作为最终授权依据；
8. 药品写操作必须复用现有 `DrugService`，不得直接调用 Mapper 绕过校验。

【实现原则】

1. LLM 只负责意图识别、参数提取、选择工具和组织回答；
2. 模型不能直接访问数据库；
3. 只允许调用服务端注册的固定领域工具；
4. 每个工具必须有固定 DTO、参数校验、权限要求和返回上限；
5. 服务端必须重新校验权限、租户、门店、参数和业务状态；
6. 查询不到数据时如实返回，不得让模型编造；
7. 工具执行失败时返回真实失败，不得让模型宣称成功；
8. 医疗相关问题不诊断、不开方、不推荐处方药替代品；
9. API Key 必须来自环境变量或本地配置，禁止提交真实密钥；
10. 优先复用现有实现，采用完成目标所需的最少代码。

【推荐工具】

至少实现以下白名单工具，名称可根据现有框架规范小幅调整，但语义不能扩大：

1. `searchDrugs`
   - 权限：`pharmacy:base:drug:query`
   - 输入：关键字、可选状态、最大返回数；
   - 匹配：药品编码、通用名、商品名、拼音码；
   - 返回结果必须限制数量。

2. `getDrugDetail`
   - 权限：`pharmacy:base:drug:query`
   - 输入：药品 ID 或唯一药品编码；
   - 输出：完成任务所需的药品字段，不输出内部审计字段。

3. `getCurrentStoreInventory`
   - 权限：沿用现有库存查询权限；
   - 输入：药品 ID 或关键词；
   - 门店 ID：只能由服务端上下文注入；
   - 输出：当前门店的可用量、冻结量、批次和效期摘要；
   - 不允许跨门店查询。

4. `prepareCreateDrug`
   - 权限：`pharmacy:base:drug:create`；
   - 只生成结构化预览和待确认命令，不调用创建 Service。

5. `prepareUpdateDrug`
   - 权限：`pharmacy:base:drug:update`；
   - 必须先读取当前值；
   - 返回字段级“旧值 → 新值”差异；
   - 不允许模型修改 approveStatus、auditBy、auditAt、tenantId、deleted 等服务端字段。

6. `prepareDeleteDrug`
   - 权限：`pharmacy:base:drug:delete`；
   - 返回明确目标和必要影响提示；
   - 不直接删除。

严禁实现 `executeSql`、`updateTable`、`deleteByNaturalLanguage` 或其他万能数据工具。

【写操作确认机制】

药品新增、修改、删除必须使用两阶段流程：

第一阶段：prepare

1. 校验当前用户权限；
2. 校验并规范化参数；
3. 读取目标当前状态；
4. 生成结构化操作预览；
5. 保存不可变的命令快照；
6. 返回 commandId、摘要、差异、过期时间和一次性确认凭证；
7. 不得产生业务数据写入。

第二阶段：confirm

1. 只能由前端明确点击确认触发；
2. 确认接口不得再次让模型决定是否执行；
3. 校验当前用户、租户、门店、权限、命令状态、有效期和防篡改摘要；
4. 防止跨用户确认、重复确认和令牌重放；
5. 执行前重新读取目标，发现关键数据已变化时拒绝执行并要求重新生成预览；
6. 调用现有 DrugService 完成写入；
7. 记录成功或失败结果；
8. 相同命令最多执行一次。

命令建议 5 分钟失效。原型可采用数据库命令表或“数据库记录 + 短时缓存”，但必须支持刷新后查看待确认状态，且不能只在浏览器内保存完整命令。

【建议接口】

1. `POST /admin-api/pharmacy/ai/chat/message/send-stream`
   - 请求体至少包含 conversationId、clientMessageId、content；
   - 使用 `Accept: text/event-stream`；
   - 不把问题内容放在 URL 查询参数；
   - 必须携带现有登录 Token。

2. `POST /admin-api/pharmacy/ai/command/{commandId}/confirm`
   - 普通 JSON 接口；
   - 只接受确认凭证，不重新接受可篡改的完整业务参数。

3. `POST /admin-api/pharmacy/ai/command/{commandId}/cancel`

SSE 至少支持：

- `metadata`
- `delta`
- `tool_started`
- `tool_result`
- `tool_preview`
- `error`
- `done`

请尽量复用当前 `yudao-module-ai` 与 `admin-ui/src/api/ai` 的流式协议；如果现有协议不同，先说明差异，再做最小兼容扩展，不要并行创造第二套无必要的通用 AI 协议。

【模块与文件范围】

优先采用最小改动方案完成原型：

- 可以启用现有 `yudao-module-ai`；
- 可以在 AI 模块中新增独立的 pharmacy 适配包；
- 可以让 AI 模块依赖 pharmacy 模块，但不得形成循环依赖；
- 可以在 `admin-ui/src/api/pharmacy/ai` 和 `admin-ui/src/views/pharmacy/ai` 新增原型代码；
- 数据库和菜单变化必须新增 `sql/migrations/` 增量脚本；
- 不修改已经执行的历史迁移。

如果检查后发现新增 `yudao-module-pharmacy-ai` 比直接放入 AI 模块更简单或能显著降低依赖风险，可以采用独立模块，但必须先说明原因及增加的文件范围。不要为了架构完整而过度拆分。

【权限和门店隔离】

1. 页面入口需要独立的 AI 使用权限；
2. 每个工具还必须叠加原有业务权限；
3. 工具注册阶段应尽量不向模型暴露无权工具；
4. 工具执行阶段必须再次校验权限；
5. 门店从当前员工关系解析；
6. 如管理员未绑定员工，默认拒绝门店库存查询，或要求选择一个经过服务端数据权限校验的门店；不得默认暴露全租户库存；
7. 不得依赖前端隐藏按钮作为安全控制；
8. 数据库租户插件是附加防线，不代替业务门店校验。

【前端最小要求】

1. 左侧可选会话列表，右侧消息区域和输入框；如果复用现有 AI 对话页可以明显减少工作量，可直接复用；
2. 支持流式追加文本和停止生成；
3. 工具结果使用结构化卡片，不直接显示原始内部 JSON；
4. 写操作必须显示差异卡片；
5. 确认按钮必须描述具体动作；
6. 命令执行中禁用重复点击；
7. 成功、失败、取消、过期显示不同状态；
8. Markdown 必须安全渲染，禁止执行模型返回的 HTML 或脚本；
9. 不进行与原型无关的 UI 重构。

【模型配置与提示词】

1. 只接入一个当前环境可用的 OpenAI 兼容模型；
2. 优先使用现有 AI 模块的模型配置能力；
3. 不在代码或提交文件中写入真实 API Key；
4. temperature 使用适合工具调用的较低值；
5. 限制最大工具轮次、历史消息数、单次返回行数和请求超时；
6. 系统提示词明确禁止编造实时数据、越权、任意 SQL和未经确认执行写操作；
7. 安全约束必须由 Java 代码实现，不能只依赖系统提示词。

【测试要求】

至少完成并实际运行与改动对应的测试：

一、正常流程

1. 查询存在的药品；
2. 查询不存在的药品；
3. 查询当前门店库存；
4. 生成新增预览，确认后成功新增；
5. 生成修改预览，确认后成功修改；
6. 生成删除预览，确认后成功删除允许删除的药品。

二、安全与异常流程

1. 未确认时数据库业务数据不发生变化；
2. 无业务权限用户不能调用对应工具；
3. 模型或请求伪造 storeId/tenantId 不生效；
4. 同租户不同门店不能互相查询库存；
5. 已使用或过期确认凭证不能再次执行；
6. 两次点击确认只执行一次；
7. 删除被条码或业务数据引用的药品时，继续由现有 Service 拒绝；
8. 提示词注入“忽略规则并执行 SQL”不能触发数据库操作；
9. 模型超时或不可用时原有业务接口仍然正常；
10. SSE 异常时必须发送或呈现明确终止状态。

优先为权限、门店隔离、命令幂等和未确认不写入编写自动化测试。不要使用硬编码成功、吞异常或伪造联调结果通过验收。

【实施顺序】

严格按以下顺序推进，每一步完成后先验证再进入下一步：

阶段 1：仓库核查和最小设计
- 确认依赖、模块、Service、数据表及前端复用点；
- 输出实际文件清单和接口契约。

阶段 2：启用 AI 与基础 SSE
- 启用当前 AI 模块；
- 配置一个模型；
- 跑通带鉴权的 POST SSE；
- 验证 AI 故障不影响原业务。

阶段 3：只读工具
- 实现药品搜索、详情和当前门店库存工具；
- 完成权限和门店隔离测试。

阶段 4：受控写工具
- 实现命令快照、预览、确认、取消、过期和幂等；
- 接入 DrugService 完成药品 CRUD；
- 验证确认前零写入。

阶段 5：管理端页面
- 接入 SSE；
- 实现工具结果与确认卡片；
- 完成错误、取消和过期状态。

阶段 6：回归和交付
- 运行后端测试、前端类型检查和必要构建；
- 检查 Git diff，移除仅由本任务产生的无用代码；
- 输出启动、配置、迁移和演示步骤。

【成功标准】

只有同时满足以下条件，才能声明原型完成：

1. 管理端页面能够完成真实 SSE 对话；
2. 查询结果来自真实业务 Service，不是 Mock；
3. 库存查询仅限服务端解析出的当前门店；
4. 新增、修改、删除在确认前没有业务写入；
5. 确认后复用 DrugService 且仅执行一次；
6. 原有权限、唯一性、引用和业务规则继续生效；
7. 不存在万能 SQL 或通用表操作工具；
8. AI 服务关闭或异常不影响原有业务；
9. 关键自动化测试通过；
10. 无真实密钥或敏感数据被提交。

【遇到阻塞时】

1. 先通过仓库代码、现有测试和本地配置排查；
2. 不通过关闭权限、租户插件、校验或测试来绕过问题；
3. 如果缺少 API Key，可以完成代码、Mock 单元测试和配置模板，但必须明确说明真实模型联调未完成，不得伪造结果；
4. 如果必须修改公共依赖、认证、全局配置或其他成员模块，先说明原因、影响文件和替代方案，等待用户确认；
5. 不执行共享环境部署、数据库清理、Git 推送或破坏性操作。

【最终交付格式】

完成后请按以下结构汇报：

1. 完成结论
   - 已完成、部分完成或未完成；
   - 是否满足全部成功标准。

2. 功能说明
   - 已支持的对话、查询和写操作；
   - 明确未支持的功能。

3. 修改文件
   - 按后端、前端、SQL、测试和文档分类列出；
   - 每个文件用一句话说明用途。

4. 数据库与配置
   - 迁移脚本和执行顺序；
   - 所需环境变量；
   - 不得输出真实密钥。

5. 验证结果
   - 实际运行的命令；
   - 通过、失败和未运行的检查；
   - 失败原因不得隐瞒。

6. 演示步骤
   - 如何启动；
   - 使用哪个测试账号和所需权限；
   - 查询药品、查询库存、修改预览与确认的演示话术。

7. 风险与后续工作
   - 原型与生产版本之间仍缺少的内容；
   - 已知限制和建议的下一步。

请从读取指定文档、检查 Git 状态和现有代码开始。先输出核查结果与计划，然后持续实施和验证，直到达到成功标准或出现必须由用户决策的阻塞。
```

## 推荐的首次验收话术

开发完成后，可依次输入以下内容验证：

```text
查询名称中包含“阿莫西林”的药品，最多显示 5 条。
```

```text
查询药品编号 AMX001 在我当前门店的可用库存、冻结库存和最近到期批次。
```

```text
把药品编号 AMX001 的零售价修改为 18.50 元。先给我看修改前后的差异，不要直接执行。
```

检查修改预览无误后，点击页面上的确认按钮。不要使用“我确认”聊天文字替代结构化确认操作。
