# FirstSun 全项目自动化功能验收方案

## 1. 目标

本方案用于每次多人分支合并后，对 `main` 进行可重复的功能验收，发现以下问题：

- 页面存在但菜单、路由、权限或 Docker 初始化未接入。
- 查询接口可用，但新增、修改、删除、审核、结算等操作不可用。
- 单模块 CRUD 可用，但采购入库、销售扣库、退货回补、处方放行、积分变化等跨模块流程中断。
- 前端提示成功，但数据库未写入；接口失败后状态、库存或金额被部分修改。
- 重复提交造成重复入库、重复扣库、重复退款或重复积分。

检测阶段只收集证据和生成任务，不修改业务代码。修复应由对应成员在独立分支完成，合并后重新执行本方案。

## 2. 执行环境

### 2.1 基准环境

- 代码：最新 `origin/main`，工作区无冲突。
- 环境：项目根目录的 `docker-compose.yml`。
- 浏览器：桌面 Chromium，先使用 1440px 宽度，关键页面补测 1024px。
- 开发账号：租户 `FirstSun`、用户名 `0407`、密码 `123456`。
- 测试数据：优先使用初始化演示数据；新增数据统一带 `AUTO-年月日时分秒` 前缀。

不得在共享数据库执行 `docker compose down -v`。需要验证全新初始化时，应使用独立克隆目录和独立测试环境，并在删除数据卷前取得明确授权。

### 2.2 证据目录

临时截图、响应体和日志放入：

```text
.tmp/acceptance/<run-id>/
```

最终报告放入：

```text
docs/acceptance/reports/<run-id>-main-functional-report.md
```

临时证据不提交，最终报告可提交。

## 3. 检测层级

### Gate 0：代码与合并完整性

1. 执行 `git status --short --branch`，确认当前提交和分支。
2. 执行 `git diff --name-only --diff-filter=U`，不得存在未解决冲突。
3. 扫描 `<<<<<<<`、`=======`、`>>>>>>>` 冲突残留。
4. 检查新增 SQL 是否包含 `SET NAMES utf8mb4;`，是否加入 `docker-compose.yml` 初始化顺序。
5. 检查菜单的 `path`、`component`、权限标识与前端文件是否一致。

### Gate 1：构建与服务健康

1. `docker compose config --quiet` 必须通过。
2. 前端 TypeScript 检查和生产构建必须执行，并区分历史错误与本次新增错误。
3. 后端至少编译 `yudao-module-pharmacy` 及其依赖；已有模块测试必须执行。
4. `docker compose ps` 中 MySQL、Redis、backend、admin-ui 均应运行，健康检查不得失败。
5. 检查后端启动日志，不得存在 Bean 缺失、SQL 失败、Mapper 重复或路由冲突。

### Gate 2：认证、菜单与路由

1. 使用共享账号登录，验证登录接口返回成功。
2. 调用权限信息接口，保存菜单树和权限集合。
3. 菜单 SQL、角色授权、租户套餐、后端权限和前端按钮权限应一致。
4. 逐项打开药店业务菜单，页面不得出现 404、空白页或动态组件加载失败。
5. 浏览器控制台不得出现本模块新增错误；接口 4xx/5xx 必须记录请求和响应。

### Gate 3：A～F 单模块纵向验收

| 成员 | 模块 | 必测正常流程 | 必测异常流程 |
| --- | --- | --- | --- |
| A | 基础资料与公共平台 | 门店、员工、分类、药品、条码的查询、新增、编辑；条码反查药品 | 重复条码、停用药品、无权限访问、错误父分类 |
| B | 供应商与采购 | 供应商及证照；采购单创建、提交、审批、部分收货、完成收货 | 过期证照、非法状态流转、超量收货、重复入账 |
| C | 库存与库房 | 仓库货位、批次库存、流水、效期、盘点、报损；统一库存门面 `receive`、`deduct`、`returnBack` | 库存不足、过期批次、重复业务号、失败回滚、跨门店访问 |
| D | POS 销售 | 开班、普通 OTC 销售、销售单查询、部分退货、支付明细、交班、销售统计 | 未开班销售、重复结算、超量退货、重复退货、库存失败时整单回滚 |
| E | 处方与统一支付 | 处方登记、审核通过/驳回、台账、模拟支付单和退款查询 | 无权审方、处方药未审方销售、重复回调、元/分转换错误 |
| F | 会员与小程序 | 会员、等级、地址、积分、购物车、线上订单查询及状态流转 | 越权查看、重复积分、取消订单重复回补、库存/支付失败回滚 |

每个页面至少执行：打开、查询、重置、查看详情，以及页面实际提供的新增、编辑、删除、审核、提交或结算操作。不能只根据页面能显示或列表有数据判定通过。

### Gate 4：跨模块闭环

| 流程编号 | 流程 | 主责与协作 |
| --- | --- | --- |
| FLOW-01 | A 建药品 → B 建采购单并收货 → C 出现批次库存和入库流水 | B 主责业务状态，C 主责库存写入，A 主责商品数据 |
| FLOW-02 | C 准备可售库存 → D 开班销售 → C 扣减库存并产生流水 | D 主责销售事务，C 主责选批、扣库和幂等 |
| FLOW-03 | D 查询原销售单 → 部分退货 → C 原批次回补 → 支付/积分按规则回退 | D 主责退货，C/E/F 分别负责库存、支付、积分副作用 |
| FLOW-04 | E 登记并审核处方 → D 销售处方药 → C 扣库 | E 主责审方状态，D 主责销售校验，C 主责库存 |
| FLOW-05 | F 建会员/订单 → C 库存变化 → E 支付状态 → F 取消或完成 | F 主责订单，C/E 提供库存和支付能力 |

每条流程都要记录操作前后关键数据：业务单状态、库存数量、库存流水、支付金额、退款金额和积分。任一环节失败后，检查是否出现部分成功。

### Gate 5：幂等、权限和一致性

- 对提交、审批、收货、结算、退货、退款、积分操作执行两次相同请求。
- 使用无权限角色验证后端确实返回拒绝，不能只看按钮隐藏。
- 比较数据库前后值，核对订单总额、支付总额、退款总额和库存变化。
- 检查租户和门店隔离；不得通过修改请求 ID 读取其他租户数据。
- 检查接口失败后的事务回滚和错误提示，不允许吞异常或硬编码成功。

## 4. 缺陷责任判定

不能仅按“哪个页面报错”分配责任，应按故障根因分配：

| 根因 | 主责 | 协作 |
| --- | --- | --- |
| Docker、菜单 SQL、角色、字典、公共模块接入遗漏 | A | 对应功能成员提供脚本和权限清单 |
| 商品、门店、员工、条码数据或接口错误 | A | 调用方成员 |
| 采购状态、收货业务数据错误 | B | C |
| 库存查询、入库、扣减、回补、流水、幂等未实现 | C | B、D、F |
| POS 金额、班次、销售、退货状态错误 | D | C、E、F |
| 处方或统一支付实现错误 | E | D、F |
| 会员、积分、小程序订单实现错误 | F | C、D、E |
| 调用参数违反已约定接口 | 调用方成员 | 服务提供方确认契约 |

跨模块问题必须指定一个主责和至少一个协作人，不能写成“全组处理”。

## 5. 严重级别

| 级别 | 定义 |
| --- | --- |
| P0 | 无法启动、无法登录、数据库初始化失败、数据严重损坏或主流程完全不可用 |
| P1 | 采购入库、库存、销售、退货、处方等核心流程中断，或发生重复扣款/扣库/退款 |
| P2 | 单个页面主要操作失败、权限错误、统计明显错误，但存在替代路径 |
| P3 | 文案、布局、轻微交互或非核心兼容性问题 |

## 6. 当前已知集成缺口示例

截图中的“库存服务未就绪，本次操作无法扣减/回补库存”不是普通前端问题。当前：

- `InventoryFacadeImpl` 是临时降级实现，`deduct`、`returnBack`、`receive` 均直接抛出 `UnsupportedOperationException`。
- `FacadeFallbackConfiguration` 在没有真实 `InventoryFacade` Bean 时注册该降级实现。
- 因此 D 的销售和退货、B 的采购收货、F 的订单取消都会在库存联动处失败。

建议任务：C 成员实现真实 `InventoryFacade` 并覆盖入库、扣减、回补、批次和幂等测试；B、D、F 分别补齐调用场景的集成测试和失败回滚验证。该问题应标记为 P1，C 主责，B/D/F 协作。

## 7. 最终报告格式

报告必须包含：

1. 测试提交、时间、环境和数据库初始化方式。
2. Gate 0～5 的通过、失败、阻塞数量。
3. 每个功能的操作步骤、预期、实际、接口响应、日志和数据库证据。
4. 按 A～F 分组的修复任务；每项任务包含缺陷编号、严重度、主责、协作人、建议文件范围和复验标准。
5. 无法测试的项目及原因，不能把“未测试”写成“通过”。

任务表统一使用：

```text
| ID | 严重度 | 主责 | 协作 | 功能/路由 | 复现步骤 | 实际结果 | 根因证据 | 建议修改范围 | 复验标准 |
```

修复完成后，必须重新执行失败用例及相关跨模块闭环，不能只验证报错提示消失。
