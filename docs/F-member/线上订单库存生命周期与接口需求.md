# F 线上订单库存生命周期与跨模块接口需求

编写人：F。编写日期：2026-09-16。基线：`main` @ `577c422f`（含 PR #28/#29/#30）。

本文用于说明 F 侧线上订单库存生命周期的落地情况，以及必须由 C 提供的新接口。**在组长确认前，F 不修改 C 的库存实现。**

## 1. 背景

线上订单的完整生命周期应为：

```text
下单（待支付）→ 冻结库存
支付成功      → 冻结转正式出库
取消 / 超时   → 释放冻结
退款 / 退货   → 回补原批次、原货位
```

其中「冻结 / 释放 / 冻结转出库」与「下单前可售量校验」依赖 C 的库存写能力。本次 F 按现有 `InventoryFacade` 能力补齐了可落地部分，冻结相关能力先提交接口需求。

## 2. 现有能力核对

| 能力 | 现状 | 证据 |
| --- | --- | --- |
| 销售出库扣减 | 可用 | `backend/.../api/inventory/InventoryFacade.java`、`backend/.../service/inventory/InventoryFacadeAdapter.java` |
| 扣库入参强校验（`bizNo` 全行一致、`bizLineId` 唯一且为正整数） | 可用 | `InventoryFacadeAdapter` 的 `validateDeduct` |
| 退货按原批次、原货位回补 | 可用 | `InventoryFacadeAdapter` 的 `returnBack`、`validateReturn` |
| 收货入库 | 可用 | `InventoryFacadeAdapter` 的 `receive` |
| **库存冻结（reserve）** | **不可用** | `InventoryFacade` 无该方法；库存 mapper 无任何 `qty_frozen` 的 UPDATE 语句 |
| **冻结释放（release）** | **不可用** | 同上 |
| **冻结转出库（consume）** | **不可用** | 同上；`ph_inv_flow.frozen_delta` 在写入时恒为 0（`backend/.../dal/mysql/inventory/InventoryFacadeMapper.xml` 的 `insertFlow`） |
| **只读可售量（供下单前校验）** | **不可用** | `InventoryFacade` 无读方法；`InventoryReadAccess` 是 C 的内部组件，未作为跨模块只读接口暴露 |
| 数据模型已就绪 | 已具备但无写入侧 | `sql/firstsun_pharmacy_init.sql`：`ph_inv_batch.qty_frozen`、`ph_inv_location_stock.qty_frozen`、`ph_inv_flow.frozen_delta`、`flow_type` 含 80 锁定 / 81 释放 / 82 锁定转出库、`ph_inv_lock` 表 |

C 的修复记录也已明确本项未实现：`docs/acceptance/reports/20260915-c-inventory-facade-repair.md` 中「F 的线上订单冻结、释放、冻结转出库仍属 P2 生命周期契约，未在本次 C/P1 修复中扩展」。

## 3. 请求 C 新增的接口

新增到 `backend/.../api/inventory/InventoryFacade.java`（与现有 `deduct` / `returnBack` 同一契约风格，均要求来源单据 + 来源行作为操作级幂等键）。

| 编号 | 建议接口 | 语义 | 调用方 |
| --- | --- | --- | --- |
| R1 | `ReserveResult reserve(Long storeId, List<ReserveItem> items)` | 订单占用冻结：`qty_frozen += qty`，可用量减少，写 `flow_type=80`、`frozen_delta=+q` | F（下单） |
| R2 | `void release(Long storeId, List<ReleaseItem> items)` | 释放冻结：`qty_frozen -= qty`，可用量恢复，写 `flow_type=81`、`frozen_delta=-q` | F（取消、支付超时） |
| R3 | `DeductResult consumeReservation(Long storeId, List<ConsumeItem> items)` | 冻结转正式出库：`qty_frozen -= q`、`qty_avail -= q`、`qty_sold += q`，写 `flow_type=82`、`frozen_delta=-q`、`out=q` | F（支付成功） |
| R4 | `List<AvailableQty> getAvailableQty(Long storeId, List<Long> drugIds)` | 只读可售量（`qty_avail`，即已扣冻结），不做任何写入 | F（下单前校验） |

建议 DTO 字段（与现有 `DeductItem` / `ReturnBackItem` 保持一致）：

- `ReserveItem`：`drugId`、`qty`、`bizNo`（订单号，全行一致）、`bizLineId`（订单明细 ID）；`batchId` / `locationId` 可选，缺省由 C 按 FEFO 选批并回传。
- `ReleaseItem` / `ConsumeItem`：在 `ReserveItem` 基础上要求 `batchId`、`locationId`（按冻结时的实际分配释放或转出库）。
- `ReserveResult`：建议返回实际分配列表（`bizLineId`、`batchId`、`locationId`、`qty`），与 `DeductResult.Allocation` 结构一致。
- `AvailableQty`：`drugId`、`qtyAvail`。

## 4. 影响范围

- C：`api/inventory` 新增 4 个方法与 DTO；`service/inventory/InventoryFacadeAdapter` 新增实现并真正写入 `qty_frozen` 与 `frozen_delta`；`InventoryFacadeMapper` 新增冻结/释放/转出库语句。幂等键可复用 `ph_inv_flow` 既有唯一索引 `uk_flow_event`（已包含 `flow_type`）。
- F：`service/member/WxOrderServiceImpl` 的下单、支付、取消、退款四处调用点替换或新增调用；并新增「支付超时自动释放」的定时任务。
- D：不受影响（D 继续使用 `deduct` / `returnBack`）。
- B：不受影响（B 继续使用 `receive`）。
- 迁移：如需在 `ph_inv_lock` 落地订单锁，请 C 确认该表归属与迁移脚本，F 不重复建冻结表。

## 5. 调用门禁问题（需一并确认）

`backend/.../service/inventory/InventoryReadAccess.java` 的 `requireScope` 要求：登录用户必须是 **ADMIN 类型**，且是 **目标门店的在职员工**（`ph_employee.user_id` 绑定且 `status=1`、`store_id` 与请求门店一致）。

影响 F 的线上订单链路：

- 小程序端（会员登录，`userType=MEMBER`）触发支付 / 取消时，无法通过库存作业门禁。
- 后台管理员若不是该门店在职员工，同样被拒绝。

F 侧当前行为：库存作业只在「该门店在职员工」上下文能成功，其余场景会返回明确的业务错误（`PHARMACY_WX_ORDER_STOCK_OP_FAILED`，提示无库存作业权限），不会静默跳过。

需要 C 与组长确认其一：

1. 由 C 提供**订单驱动的系统级入口**（校验租户 + 门店 + 业务单号，不做员工绑定）；或
2. 明确约定 F 把出库 / 释放动作**延后到门店员工操作节点**（拣货、核销），线上支付只记录支付状态。

## 6. F 侧本次已落地与未落地

已落地（不依赖新接口）：

- 支付成功 → 按 FEFO 正式出库，扣库请求携带 `bizNo`（订单号）+ `bizLineId`（订单明细 ID），满足 C 的操作级幂等契约。
- 出库实际分配（批次 + 货位 + 数量）写入 F 自有表 `ph_wx_order_line_alloc`（迁移 `sql/migrations/20260916_f_wx_order_line_alloc.sql`），支持 FEFO 拆分到多批次。
- 取消 / 退款 → 携带 `originalBizNo`、`originalBizLineId`、原 `batchId`、原 `locationId` 回补；重复取消、重复退款不重复回补。
- 重复支付回调不重复扣库；订单状态机与出库分配表双重保证幂等。

未落地（被 R1～R3 阻塞）：

- 下单时不冻结库存 → 缺少超卖保护。
- 支付超时无人自动释放 → 无占用故无可释放，但同样无保护。
- 下单前不做可售量校验 → 库存不足的订单仍会创建成功，直到支付时才失败。

未落地（被 R4 阻塞）：

- 下单前校验可售量，实现「库存不足时不得创建有效订单」。

## 7. 需要组长确认的事项

1. 是否同意按 R1～R3 由 C 扩展 `InventoryFacade` 的冻结 / 释放 / 冻结转出库能力。
2. 库存作业门禁（第 5 节）选方案 1 还是方案 2。
3. 若选方案 2，F 需要同步调整线上订单状态机语义（支付不扣库、核销扣库），需确认是否影响验收用例。
